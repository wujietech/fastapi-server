## 3. 核心模块 (M4, M5, M6) 启动方案

模块4用户中心、模块5 OAuth2 服务和模块6 MCP 存储库服务是本次冲刺中立即启动设计的核心模块。它们将为后续模块（特别是任务、文件、Prompt 等业务模块）提供基础支撑。

### 3.1 模块4：用户中心服务 (`sys.service.user_center`)

*   设计目标： 构建支持账户-身份档案分离、基于身份档案 (`user_id`) 进行权限与权益管理、具备百万级用户规模高性能访问能力的用户中心服务。
*   关键技术选型：
    *   持久化：依赖模块2 `sys.storage.persistence` 提供的 PostgreSQL (账户、身份档案、权限元数据) 和 Redis Cluster (实时权限/权益状态、消耗计数) 能力。
    *   核心逻辑：平台统一的服务框架，高并发异步 I/O。
    *   数据模型：基于 `user_accounts` 和 `user_identity_profiles` 的分离模型。
*   核心功能点： 用户账户及身份档案 CRUD、多身份档案管理、基于 `user_id` 的实时权限检查 (`check_permission`)、基于 `user_id` 的消耗型权益原子扣减 (`deduct_right_consumption`)、用户账户及身份档案状态管理、与 OAuth2 服务集成支持登录/选择身份档案。
*   六维度质量策略 (设计阶段)：
    *   系统健壮性： 设计明确的错误处理和回滚机制（特别是账户与身份档案创建、权益扣减等原子操作），考虑并发场景下的数据一致性（利用 Redis 原子操作）。
    *   设计简洁性： 逻辑模型清晰反映账户与身份档案分离；API 设计遵循 RESTful 原则，职责单一。
    *   开发门槛低： 依赖模块2封装的复杂持久化细节；提供清晰的 API 文档和数据模型定义。
    *   开发效率高： 采用标准技术栈；设计可复用的内部组件（如权限计算逻辑）；明确与模块2/5的接口契约。
    *   开发可控性高： 模块职责划分清晰；数据流向明确；关键业务流程图化；定义明确的开发任务边界。
    *   系统稳定性强： 依赖模块2提供的高可用 Redis Cluster；设计后台任务确保 PG 与 Redis 之间的数据最终一致性；考虑异常状态处理（如 Redis 访问失败）。

### 3.2 模块5：OAuth2 服务 (`sys.service.oauth2`)

*   设计目标： 实现符合 OAuth2.0 规范的认证授权服务，安全地为用户账户提供访问令牌，并将选定的身份档案 (`user_id`) 信息包含在令牌中，支持第三方客户端接入。
*   关键技术选型：
    *   协议标准：OAuth2.0, OIDC (OpenID Connect) 核心规范。
    *   Token 实现：JWT (JSON Web Tokens) 用于 Access Token，Refresh Token 用于续期。
    *   用户认证依赖：调用模块4 `sys.service.user_center` API 进行账户凭证验证和获取身份档案列表。
    *   Token 存储：依赖模块2 `sys.storage.persistence` 或独立存储服务存储 Refresh Token、授权码等状态信息。
*   核心功能点： 授权码模式 (`Authorization Code Flow`)、刷新令牌 (`Refresh Token`)、客户端凭据模式 (`Client Credentials Flow`) (可选)、令牌颁发与验证、基于模块4 API 的用户账户认证、集成模块4提供的身份档案选择机制，并在 JWT Payload 中包含 `account_id` 和选定的 `user_id`、内部服务调用凭证管理 (可选)。
*   六维度质量策略 (设计阶段)：
    *   系统健壮性： 设计安全的 Token 验证、撤销和续期流程；处理并发请求和异常情况。
    *   设计简洁性： 遵循 OAuth2 标准流程；接口设计清晰，参数规范。
    *   开发门槛低： 依赖成熟的 OAuth2/JWT 库；明确与模块4的交互接口。
    *   开发效率高： 优先使用现有开源实现进行定制开发；专注于业务逻辑与标准协议的整合。
    *   开发可控性高： 定义明确的状态机（授权码、Token生命周期）；清晰的错误码体系。
    *   系统稳定性强： 考虑 Token 存储的高可用；设计抗攻击（如重放攻击）的机制。

### 3.3 模块6：MCP 存储库服务 (`sys.service.mcp_repository`)

*   设计目标： 构建 Manus MCP Server 内部的 MCP 工具元数据存储与管理中心，为 ScaleMCP 提供可靠的工具信息同步源，也为其他内部服务提供工具查询能力。
*   关键技术选型：
    *   元数据存储：依赖模块2 `sys.storage.persistence` 提供的 PostgreSQL 能力存储 MCP 工具的结构化元数据（名称、版本、描述符、调用方式、关联服务ID等）。
    *   数据模型：MCP 工具描述符 (`tool_descriptor`) 的数据模型设计，参考 MCP 协议规范。
    *   同步机制：考虑为 ScaleMCP 提供高效的元数据同步接口（如基于时间戳的增量同步）。
*   核心功能点： MCP 工具元数据 CRUD (创建、读取、更新、删除)、按条件查询工具元数据（按名称、标签、关联服务等）、按版本管理工具元数据、为 ScaleMCP 提供工具元数据同步接口、工具元数据版本回溯 (可选)。
*   六维度质量策略 (设计阶段)：
    *   系统健壮性： 设计元数据严格校验机制；确保 CRUD 操作的事务性；考虑并发更新冲突。
    *   设计简洁性： 数据模型清晰反映 MCP 工具描述符结构；API 设计直观，资源导向。
    *   开发门槛低： 依赖模块2封装的PG操作；明确元数据模型，简化开发。
    *   开发效率高： 采用标准 CRUD 模式；专注于元数据模型设计与接口实现。
    *   开发可控性高： 元数据结构定义明确；数据一致性要求高；设计版本管理流程。
    *   系统稳定性强： 依赖模块2提供的高可用PG存储；同步接口设计考虑流量控制和错误恢复。

### 4.3 “六维度质量标准”的落实与评估方法

将用户定义的六维度质量标准贯穿于整个冲刺的设计、开发、测试及集成过程。

1.  系统健壮性 (System Robustness)：
    *   落实： 在设计阶段考虑异常分支、错误处理、重试策略、并发控制。在开发阶段实现单元测试、集成测试，特别是针对核心流程和边界条件。实施代码评审，关注异常处理逻辑。规划和执行压力测试、故障注入测试。
    *   评估： 通过测试覆盖率、错误处理代码评审、压力测试报告（如最大并发用户数、响应时间）、故障注入测试结果来评估。关键业务流程的端到端测试通过率。

2.  设计简洁性 (Design Simplicity)：
    *   落实： 遵循架构原则（M1）、命名空间规范（M1）。模块职责单一、接口定义清晰。代码实现遵循 DRY 原则，避免过度复杂。在设计和代码评审中将简洁性作为重要考量项。
    *   评估： 通过架构评审、模块接口评审、代码复杂度分析（如圈复杂度）、代码评审中的反馈次数来评估。

3.  开发门槛低 (Low Development Threshold)：
    *   落实： 依赖 Cursor AI 提供的清晰准确的设计文档作为输入。利用模块1/2/4/5/6 构建的基础服务和标准组件，减少重复“造轮子”。提供标准开发环境配置和入门指南。
    *   评估： 新参与开发者上手速度、文档清晰度反馈、基础服务接口易用性评估。

4.  开发效率高 (High Development Efficiency)：
    *   落实： 利用 Cursor AI 进行代码生成和辅助开发。任务分解细致，减少阻塞。跨职能协作紧密，快速解决问题。文档驱动开发，减少沟通歧义。
    *   评估： 单个模块或功能的开发周期、代码产出速率（结合质量）、任务完成率。

5.  开发可控性高 (High Development Controllability)：
    *   落实： 明确的模块设计和开发任务边界。使用版本控制系统（如 Git）管理代码，频繁提交。定期代码评审。严格执行用户定义的改进熔断机制（3次未达目标即讨论）。使用项目管理工具跟踪任务状态。
    *   评估： 代码提交频率、代码评审覆盖率和问题解决率、任务状态的清晰度和准确性、风险识别和处理的及时性。

6.  系统稳定性强 (Strong System Stability)：
    *   落实： 在设计中考虑依赖服务的高可用。实现全面的自动化测试（单元、集成、系统测试）。建立持续集成/持续部署（CI/CD）流程。实现完善的服务监控和告警（基于 M2/M4 设计的监控点）。规划上线后的灰度发布和回滚方案。
    *   评估： 测试环境和生产环境的自动化测试通过率、监控告警的有效性、生产环境故障率和平均恢复时间（MTTR）、系统关键指标（延迟、错误率）的稳定性。
